## What “cancella account” means (chosen contract)

| Axis | Choice |
|---|---|
| Model | **Two-phase operational deletion** |
| Phase 1 (M3) | Soft-close Account + revoke capabilities + minimize/unpublish Persona + delete personal contact channels + cease professional public contacts + Auth ban (server) + session invalidation |
| Phase 2 (later) | Optional hard DELETE of `accounts` / Auth only after RESTRICT deps cleared and Terms proof archived-or-dropped |
| Hard delete `accounts` in M3? | **No** |
| Delete autonomous entities? | **No** |
| Auto-transfer ownership? | **No** |
| Auto M2 archive? | **No** — only when concrete reason |

Legal alignment: Privacy Policy §11.1 A/B/C; Termini §16.1; retention-schedule; L1.3 alignment M3/M4 split.

## Account lifecycle after success

| Check | Result |
|---|---|
| `account_status` | `closed` (+ `closed_at`) |
| `access_is_active_account()` | **false** |
| Elevated roles | revoked |
| Impresa ACT grants | revoked (when not blocked) |
| Memberships | `relation_status=revoked`, `ended_at` set; visibility not public |
| Public Persona | `is_public=false`, `deleted_at` set, PII cleared |
| Contact channels | rows deleted |
| Prior session JWT | cannot pass active-account write gates; Auth ban prevents reuse |
| Area riservata | redirect/logout; `/app/stato/chiuso` already exists |

---

## Hard vs soft

- **User-visible “account cancellato”** = soft-close + capability wipe + public presence removed + Auth unusable.
- **Physical row elimination** of `accounts` / tombstone Persona is **not** required in the same transaction and is deferred.

---

## Auth user

| Item | Design |
|---|---|
| Mechanism | Server-only Admin API via `createAdminClient()` (existing pattern in `provision-account`) |
| Preferred action | **Ban** Auth user (`ban_duration` long / permanent) after DB RPC success |
| Why not hard DELETE Auth in SQL | `profiles.id` still `REFERENCES auth.users ON DELETE CASCADE`; Persona must survive for RESTRICT FKs (memberships, org owner, content owner, …). Auth DELETE would attempt CASCADE profile delete and fail or destroy integrity |
| Service role | Never in browser |
| Ordering | DB RPC success → Auth ban → client signOut |
| Failure A (DB ok, Auth fail) | Account already closed/minimized; retry Auth ban; do **not** reopen account |
| Failure B (Auth ok, DB fail) | Avoid by ordering DB first; if Auth banned early by bug, recovery = complete DB cleanup with service path |

---

## Session

- Primary security: `account_status=closed` + revoked grants + Auth ban.
- Secondary: client logout + cookie clear + redirect.
- Stale JWT without ban: write paths gated by `access_is_active_account()`; still **must** ban Auth.

## Persona / profilo pubblico

| Field after M3 | Fate | Why survives / removed |
|---|---|---|
| `id` | survives | FK hub for autonomous provenance (RESTRICT) |
| `slug` | anonymized `rimosso-<uuidcompact>` | unique constraint; not public listing |
| `display_name` | `Profilo rimosso` | NOT NULL |
| bio, website, avatar, geo, org presentation | null | personal data no longer necessary |
| `phone` | null | already retired (L1.1b CHECK) |

| `deleted_at` | set | soft-delete |
| Full profile copy in M2 | **forbidden** | Privacy §11.1 minimization |

`DELETE FROM person_contact_channels WHERE person_id = …` inside RPC. Soft-delete profile alone would leave channels — explicit delete required. Verify via RLS/queries, not UI only.

## Professionista

`professional_profiles`: unpublish, private visibility, cease active status, clear professional email/phone and presentation fields. Do **not** delete autonomous professional catalog services as aggregates beyond personal attribution wipe.

## Account roles

All `account_role_assignments` for the account → `revoked`.  
**Last `amministratore_applicativo`:** preflight/execute **refuse** (`last_application_admin`). No new authority invented.

## Business memberships vs grants

| Relation | On delete |
|---|---|
| Membership | Conclude/revoke lifecycle; **Impresa preserved** |
| ACT grant | Revoke `authorization_status=revoked` |
| Simple member (no sole ACT) | Allowed |
| Manager with other ACT peers | Allowed (revoke self grant) |
| **Sole ACT manager** | **BLOCKED → M4** |

`revoke_business_management` today does **not** enforce last-manager retention in DB — M3 adds explicit refuse instead of orphaning without schema.

## Organizations

| Case | Behavior |
|---|---|
| Official with `person_id` | Convert to opaque `display_label` (“Referente rimosso”), clear email/phone |
| `organizations.owner_person_id = self` | **BLOCKED → M4** (RESTRICT + no reassignment flag) |
| Organization AR | **not** deleted |

## Last manager / referent — M4 REQUIRED

Current model **cannot** correctly leave sole-managed Impresa / person-owned Org without either:

1. orphaning ACT/owner with no operational queue, or  
2. inventing auto-transfer (forbidden).

Therefore classify:

`M4 REQUIRED` — `needs_reassignment` (or equivalent) + admin workflow · **STOP before applying M3 as product**.

M3 SQL still refuses these cases (safe guard). Do **not** create M4 migration in this unit.

## Terms acceptances (M1)

- Soft-close **keeps** `terms_acceptances` (FK `ON DELETE RESTRICT` irrelevant until hard DELETE).
- **Do not** auto-archive every acceptance into M2.
- If future hard DELETE and proof still needed → M2 `terms_acceptance_proof` then drop ops row.
- If no concrete reason → delete ops row without archive.

## subject_ref

| Property | Spec |
|---|---|
| Algorithm | `ls_` + hex(HMAC-SHA256(`account_id`, secret)) |
| Secret env | `LEGAL_SUBJECT_HMAC_SECRET` (server-only, ≥32 bytes entropy; **not** in repo; **not** `NEXT_PUBLIC_*`) |
| Input | Stable `accounts.id` (not email/phone) |
| Forbidden | `SHA256(email)`, browser-derived secret, reversible encoding of PII |
| Where | Application helper `src/lib/legal/subject-ref.ts` when inserting M2; **not** required for soft-close path |

## Idempotency / concurrency

- Advisory xact lock on account id.
- Re-entry when already `closed` + Persona `deleted_at` → `{ ok, idempotent: true }`.
- Double-click / parallel → serialized; second call idempotent.
- No duplicate M2 on soft-close (archive not in RPC).

---

## Failure / recovery (preferred order)

1. Strong confirmation (re-auth)  
2. Preflight  
3. `access_self_delete_account()` (DB)  
4. Auth ban (admin client)  
5. Client signOut + redirect  

| Failure | Semantics |
|---|---|
| Preflight blocked | No mutation; show human reason (last admin / contact support for orphan) |
| DB fail | No success; Auth untouched |
| DB ok, Auth fail | Operationally closed; retry ban; alert ops |
| Client logout fail | Still closed; next request hits closed guards |
| M2 insert fail | N/A on default path; if optional archive attempted, abort before wipe of proof |

Do not declare UX success until DB RPC returns ok (Auth retry may follow with ops note).

---

## Server authorization

- No client-supplied `account_id`.
- Identity from `auth.uid()` → `accounts.auth_user_id` inside SECURITY DEFINER.
- `PUBLIC` revoked; `EXECUTE` to `authenticated` only.
- Spoof of other account_id impossible (parameter absent).

## Micro-review findings

### BLOCKING (for apply authorization)

1. **M4 required** — sole Impresa ACT / sole `owner_person_id` cannot be completed safely without reassignment schema/workflow.  
2. Applying M3 without M4 would leave product incomplete for those users (refuse-only is correct for SQL, insufficient for “self-service for all”).

### IMPORTANT

1. Auth hard DELETE incompatible with surviving Persona under `profiles → auth.users CASCADE`; ban is mandatory design.  
2. Admin `access_close_account` still does not wipe persona/grants — distinct from M3 path; do not conflate.  
3. Content/owner presentation must not re-expose wiped display names via joins (app layer).  
4. Last-admin guard exists in M3; still not in `revoke_application_role` (pre-existing).

### NON-BLOCKING

1. Soft-closed accounts retain `terms_acceptances` until a future hard-delete disposal path.  
2. UI not wired live (intentional this phase).  
3. `hashtext` advisory lock is best-effort serialization (acceptable).

### OBSERVATION

1. Detaching `profiles.id` from `auth.users` would enable Auth hard delete later — out of M3 scope.  
2. Officials anonymization may leave multiple “Referente rimosso” labels — acceptable.
