# L1.1b — Contact & Visibility Model

**Status:** IMPLEMENTED (Persona network contacts) · **Date:** 2026-08-11
**Philosophy (approved):**

| Layer | Meaning |
|---|---|
| **PUBLIC** | Discovery — presentation of actors in the economic/professional network |
| **REGISTRATION** | Participation + access to professional contacts shared with the network |
| **PROFILE** | Professional presence |
| **RESERVED AREA** | Management (own data, businesses, editorial/admin) |

**Related:** L1.1 audit · `personal-data-inventory.md` · `data-flow-map.md` · `legal-drafting-factual-brief.md`
**Migrations:** `20260814100000_create_person_contact_channels.sql`, `20260814110000_harden_legacy_profiles_phone.sql`

---

## 1. Internal messaging

**NO INTERNAL MESSAGING.**

Searched / not found as product features: messages, conversations, threads, inbox, contact_requests, connection_requests, direct_messages, chat.

Contact is realized via **professional channels** (tel / mailto / website) under the visibility rules below. L1.1b does **not** introduce chat, CRM, or contact-request workflows.

---

## 2. Visibility levels

### Level A — Internet public (anonymous)

Visible without account when the entity publication gate allows it:

- display name, slug, avatar URL if set
- bio / presentation
- territory (city/province/region/country)
- professional competencies / categories when published
- linked public businesses / organizations (as already exposed)
- public services / offers when published
- **website** when present on a public profile (presentation surface)
- other fields already allow-listed for public discovery

**Not shown / not readable via anon data path for Persona contacts:**

- Auth email
- UUID as product UI (may exist in URLs/ids where already required)
- account state, roles, grants, admin fields
- `person_contact_channels.phone` / `contact_email` values
- any contact classified network-only

Anon may learn **only a boolean** via `person_has_shared_network_contact` (CTA “Accedi per vedere i contatti”) — **no values**.

### Level B — Registered active account

May additionally read, via `person_contact_network_get`, professional contacts the owner opted to share:

- professional phone when `share_phone_with_network`
- professional `contact_email` when `share_contact_email_with_network`

Requires: caller is active Account; target Persona is public + active + not deleted; corresponding share flag true.

### Level C — Owner / application admin

- Own contact channels row (full): owner CRUD under RLS
- Auth email / account / grants / roles: existing access model (unchanged)
- Admin: `access_is_application_admin` SELECT on contact channels

## 3. Auth email ≠ contact email

| Concept | Storage | Visibility |
|---|---|---|
| Auth / login email | `auth.users` only | Private (Auth) |
| Professional contact email | `person_contact_channels.contact_email` | Network only if share flag |

The Auth email is **never** copied into `contact_email` by the app. Signup does not collect professional phone/email.

---

## 4. Phone (L1.1 finding resolution)

**Pre-L1.1b gap:** `profiles.phone` editable; public UI omitted it; RLS/anon could still SELECT the published row including phone.

**Resolution:**

1. Source of truth moved to `person_contact_channels.phone`
2. Existing non-null `profiles.phone` migrated with `share_*=false`, then cleared
3. Legacy `profiles.phone` forced `NULL` via check constraint (`profiles_phone_must_be_null_chk`)
4. Network reads only through masked SECURITY DEFINER RPC
5. Anon has **no** SELECT on `person_contact_channels`

**Why not column masking on `profiles` alone:** PostgreSQL RLS cannot hide individual columns of an otherwise-visible row. Observed: `REVOKE SELECT (phone)` under table-level `GRANT ALL` to `anon` did not produce a durable column ACL. Separate table + empty legacy column is the secure minimal pattern.

## 5. User control & defaults

**UI (profile form):** plain language checkboxes:

- “Mostra questo telefono agli utenti registrati della rete.”
- “Mostra questa email professionale agli utenti registrati della rete.”

**Defaults:** `share_phone_with_network` / `share_contact_email_with_network` = **false**.
**New contacts:** not shared until the user opts in.
**Existing records:** migrated with share flags **false** (no assumed consent).
**Privacy by default:** yes.

Microcopy distinguishes: public presentation (`is_public`, website) vs network-only contacts vs Auth email private.

## 7. Professionista

Contact SoT = **Persona** (`person_contact_channels`).
Professional profile = competencies / practice / coverage — **no duplicate phone/email** introduced in app.
DB columns `professional_phone` / `professional_email` remain schema legacy; **not** selected in app; **not** wired as L1.1b SoT.

---

## 8. Impresa

`business_channels` (channel_type / channel_value / visibility_status) is a **commercial directory** model — **not** the same rule as Persona personal phone.

**Decision (L1.1b):** do **not** auto-apply Persona registered-only semantics to Impresa.
Today: channels schema exists; public UI exposure of commercial phone/email is **not** implemented as a contact CTA; remote active contact-bearing usage was **0** at audit counts.
Future Impresa contact UX must define institutional/commercial visibility separately.

---

## 9. Organizzazione

Institutional email/phone exist in editorial forms; public selects exclude them.
Officials: public shows name/label only — **do not** publish official personal email/phone because the org is public.

**Decision:** keep institutional vs personal-official distinction; no L1.1b schema change for orgs.

## 10. Opportunity / Collaboration / Service / Event

| Domain | Contact path today | L1.1b stance |
|---|---|---|
| Opportunità | No candidatura / messaging UI | NOT IMPLEMENTED — use publisher/org/external URL when those exist; no invented workflow |
| Collaborazioni | Strong need; no messaging | NOT IMPLEMENTED contact step — future: CTA to publisher Persona network contacts / website |
| Servizi | Offro/Cerco schema; no marketplace | Relation via publisher Persona contacts when exposed |
| Eventi | External URL / organizer refs | Not ticketing; organizer contact follows org/person rules |

Uniform CTA pattern when Persona contacts exist: anon → “Accedi per vedere i contatti”; registered → Chiama / Scrivi / Visita sito as available. **No dead CTAs.**

## 11. Search engine / scraping

Registered-only values must not appear in:

- anonymous HTML
- metadata / JSON-LD for anon
- sitemap payloads
- anon Supabase selects on contact table

`person_has_shared_network_contact` may appear as CTA copy only (boolean).
No absolute guarantee against scraping by registered users who can call the RPC.

## 12. Data-access contract

| Path | anon | authenticated active | owner | admin |
|---|---|---|---|---|
| `profiles` public allow-list | Discovery fields | Same | Self edit whitelist (no phone) | Existing |
| `person_contact_channels` table | No SELECT | Own row RLS | CRUD own | SELECT |
| `person_contact_network_get` | No EXECUTE | EXECUTE (masked) | Same | Same |
| `person_has_shared_network_contact` | EXECUTE (boolean) | EXECUTE | — | — |
| Auth email | — | Own session | Own | Admin |

Preserved: Account ≠ Persona · CTX ≠ ACT · membership ≠ management grant · Redazione ≠ Admin · public profile ≠ account.

---

## 13. Schema changes (minimal)

**Table** `person_contact_channels` (1:1 `person_id` → `profiles`):

- `phone`, `contact_email`
- `share_phone_with_network`, `share_contact_email_with_network` (default false)

**RPCs:** `person_contact_network_get`, `person_has_shared_network_contact` (SECURITY DEFINER, `search_path=public`).

**Legacy:** `profiles.phone` emptied + `CHECK (phone IS NULL)`.

---

## 14. Signup

Signup remains email + password (+ optional display name metadata).
**No** professional phone/email at signup.
