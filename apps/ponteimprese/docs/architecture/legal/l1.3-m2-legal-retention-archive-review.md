## Model selected

| Choice | Rationale |
|---|---|
| Table `legal_retention_records` | No existing archive table; Access prefers soft-close; need separate minimized store for A/B/C §C |
| Typed columns, **no JSONB dump** | Passes PII minimization test; forbids profile/bio/phone/email/avatar dumps |
| `subject_ref` opaque + `source_account_id` **ON DELETE SET NULL** | Survives future hard Account DELETE without CASCADE-destroying evidence or RESTRICT-blocking M3 forever |
| Soft-close remains primary Account lifecycle | Compatible with `access_close_account`; archive is residual, not automatic |
| Terms proof copied only when reason concrete | M1 ledger stays operational until M3 needs hard delete + residual proof |
| Writes via `service_role` SECURITY DEFINER only | No browser service_role; prepares M3 server path without implementing self-delete |

## Compatibility matrix

| Topic | Design |
|---|---|
| M1 `terms_acceptances` RESTRICT | Unchanged. Soft close OK. Hard DELETE requires prior move/dispose of terms rows. |
| Future M3 | Insert archive via `legal_retention_insert_record` → remove ops PII/terms as needed → hard DELETE Account → FK nulls |
| Autonomous entities | Not archived (businesses/orgs/content/events/opportunities) |
| Backup | Explicitly **not** this table |

## Non-blocking findings

1. Dispose keeps the row skeleton (`disposed`) for audit of disposal rather than hard DELETE of the archive row — intentional.
2. No separate `privacy_officer` role — reuses `amministratore_applicativo` SELECT; acceptable for v1.
3. Marker kinds store no incident narrative beyond short `case_reference`/`admin_note` — expand only with new authorization if ever needed.

## Corrections made during review

2. Rejected JSONB profile dump and `other` reason codes.
3. Chose SET NULL over RESTRICT/CASCADE for `source_account_id`.
